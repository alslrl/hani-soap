HaniSOAP | 화면 구성·기존 구현·신규 개발 범위

2026.10.08 기준. 지난 Replit HANI 소스를 읽고, 이번 해커톤 기획과 비교한 작업 문서입니다. 화면에 들어갈 내용과 구현 현황을 함께 정리했습니다.

상태 표기: [기존 코드 확인]은 실제 함수·API·화면 코드를 확인한 항목입니다. [화면·데이터 확인]은 경로나 타입 등 일부 구조를 확인한 항목입니다. [신규 기획]은 아직 구현 사실로 확인되지 않은 이번 개발 후보입니다. [검증 필요]는 실행 또는 세부 구현 확인이 남은 항목입니다.

중요한 한계: Replit 계정은 결제 실패로 서비스가 일시 중지돼 있습니다. 이번 조사는 정적 코드 조사이며, API 호출 성공·녹음 복구 성공·메일 수신·인쇄 성공을 테스트한 결과가 아닙니다. 코드가 있다고 운영 가능한 제품이라는 뜻은 아닙니다.

아래 화면 배치와 개발 우선순위는 제안입니다. 세부 기능과 당일 개발 범위는 팀이 최종 선택하며, 기존 구현을 이번 대회에서 새로 구현한 성과로 표시하지 않습니다. 동시 진행한 기획 대화에서 공유된 최신 방향은 카카오톡 모의 발송입니다. 이 문서에서도 실제 발송 연동은 구현 범위로 확정하지 않으며, 첫 버전은 전사문에서 걱정·불안의 대상, 효과 기대·의문·직접 표현한 실망, 이해 부족, 실천 어려움을 근거 발언과 함께 추출하고 의료진이 확인하는 방향입니다. 목소리 감정 분석이나 이탈 예측은 포함하지 않습니다.

1. 제품의 전체 흐름

기존 제품의 골자는 환자 선택 → 진료 녹음 또는 파일 업로드 → 한국어 전사 → 한의학 SOAP 생성 → 저장·복사 → 이전 기록 기반 재진 요약 → 복약 안내 이메일입니다. 진료 이력, 방문 상세, 호전도 리포트, 검색, 메일 관리, 설정 페이지 경로도 있습니다.

이번 확장 방향은 같은 환자의 과거 기록과 오늘의 대화를 정확하게 구분하고, 걱정·기대·이해도와 반응의 변화를 후속 안내와 티칭으로 연결하는 것입니다. 차팅 보조와 지속적인 환자 관리를 연결하되, 모든 판단과 발송 전 확인은 의료진에게 남깁니다.

화면 구조 제안: 왼쪽에는 환자 목록과 공통 메뉴를 두고, 환자를 선택하면 상단에 환자 식별 정보를 고정합니다. 환자 안에서는 진료 이력 / 오늘 진료 / 방문 상세 / 호전도 / 후속 관리로 이동합니다. 후속 관리는 신규 화면 후보이며 기존 라우트로 확인되지 않았습니다.

2. 기존 구현의 기능별 현황

2-1. 녹음·업로드·전사

[기존 코드 확인] 브라우저 MediaRecorder로 녹음하고 오디오 파일도 업로드합니다. 서버의 POST /transcribe는 gpt-4o-mini-transcribe에 language=ko로 요청합니다. 파일 크기는 최대 25MB이고, 오디오 형식·누락·네트워크·모델 오류를 구분해 안내합니다.

[기존 코드 확인] 녹음 중 5초마다 청크를 임시 저장하는 호출, 미완료 녹음 목록, 복구 후 재전사, 폐기, 실패 후 재시도 코드가 있습니다. 녹음은 종료 후 합쳐서 전사 요청을 보내므로, 5초 단위 실시간 전사나 무제한 장시간 처리 기능으로 설명하면 안 됩니다.

[신규 기획 / 검증 필요] 전문 용어 목록을 전사 요청에 반영하는 기능, 의사·환자 화자 분리, 긴 파일 분할·재조합, 환자와 녹음의 안전한 연결을 보완할 수 있습니다. 기존 복구 코드가 실제 중단·새로고침·긴 녹음 조건에서도 동작하는지 먼저 확인해야 합니다.

2-2. 한의학 SOAP 생성

[기존 코드 확인] POST /generate-soap는 전사문, 환자 이름·나이·성별, 차팅 옵션, 이전 진료 요약을 받아 gpt-5-mini로 JSON을 생성합니다. S는 환자의 호소, O는 관찰·검사 소견, A는 평가·변증, P는 계획입니다.

[기존 코드 확인] 변증명과 근거, 검사 체크리스트, 수면·식욕·대소변 등 ROS, NRS 통증 점수를 구조화하는 서버 코드가 있습니다. 변증 카테고리, 문어체·구어체 비율, VAS 표기, 양방 진단 병기, 다음 진료 시점 옵션도 있습니다.

[검증 필요] 프롬프트에는 발화에 없는 사실을 만들지 말라는 규칙이 있지만 실제 정확도를 검증한 것은 아닙니다. 서버는 checklist·ros·nrs도 반환하나, 확인한 Home 저장 로직은 S/O/A/P와 syndromes를 저장합니다. API 반환 필드가 전부 영구 보존되는 것으로 설명하지 않습니다.

2-3. 재진 요약과 이전 기록 활용

[기존 코드 확인] POST /patient-summary는 이전 진료 기록을 받아 방문 횟수·직전 방문일·이전 주소증·처방·호전 경과·오늘 확인할 사항을 요약합니다. 이전 NRS도 추출하며, 오늘 진료의 SOAP 생성에 이전 요약을 전달하는 화면 연결이 있습니다.

[기존 코드 확인 / 한계] 과거 SOAP를 모아 프롬프트에 넣는 방식입니다. 의미 검색으로 관련 기록만 선택하는 RAG나 환자·날짜별 근거 구간을 연결하는 별도 검색 시스템으로 확인된 것은 아닙니다. 재진 맥락 활용은 기존 기능이고, 출처 관리와 과거·현재 구분을 정교화하는 것은 개선 범위입니다.

2-4. 기록 저장·조회·수정

[기존 코드 확인] 환자와 환자별 방문 기록은 localStorage에 저장합니다. 방문에는 id, patientId, ISO 날짜, 전사문, SOAP, 선택적 처방·통증 점수·수정 이력·삭제 표시가 있습니다. 전사문은 화면에서 1초 디바운스 후 자동 저장하며, SOAP 전체를 클립보드에 복사하는 코드도 있습니다.

[기존 코드 확인] 방문 상세에는 전사문·S/O/A/P 편집 상태와 수정 전후 비교 화면 코드가 있습니다. 저장소의 삭제는 deletedAt을 남기는 소프트 삭제입니다. 다중 기기 동기화, 서버 백업, 의료기관별 권한, 변경자 식별이 확인된 것은 아닙니다.

2-5. 복약 안내 이메일

[기존 코드 확인] POST /send-prescription는 환자, 처방명·기간·하루 복용 횟수·추가 안내, SOAP 맥락, 한의원 정보를 받아 안내문을 생성합니다. dryRun이면 미리보기만 반환하고, 실제 발송 경로는 메일러의 sendMail을 사용합니다.

[기존 코드 확인 / 검증 필요] 이메일 주소 누락과 메일러 미설정을 별도로 처리하며, 한의원 이름·주소·담당의·로고를 반영하는 코드와 발송 이력 타입·저장 함수가 있습니다. SMTP 설정이나 실제 이메일 수신은 확인하지 않았습니다. 이메일 구현을 SMS 문자 발송 구현으로 설명하면 안 됩니다.

2-6. 호전도·측정 기록과 보조 화면

[기존 코드 확인] 환자 이력 화면에는 방문 목록, SOAP 작성 여부, 기록 미리보기, 통증 그래프 관련 코드, 환자별 메일 이력 표시가 있습니다. 리포트에는 그래프 구성, 처방 변화, 한의원 정보·의사 서명·참고용 자료 고지 영역이 있습니다. 인쇄 관련 UI 코드도 있으나 실제 인쇄 결과는 미검증입니다.

[화면·데이터 확인] DailyMeasurement 타입에는 활력징후, HRV·체성분·체열 메모, 통증·기능, 수면·기력·기분·식욕·대변, 복약 횟수·부작용·자각 효과 필드가 있습니다. mood는 0~10 점수 필드입니다. 이 필드가 있다고 감정 자동 분석이나 환자용 외부 체크인 서비스가 구현된 것은 아닙니다.

[화면·데이터 확인] 검색·메일 관리·설정·요금 안내 페이지 경로와 저장 검색·메일 로그·한의원 설정 타입을 확인했습니다. 각 화면의 모든 버튼·필터·결제 연동까지 조사한 것은 아니므로, 보조 기능 전체의 완성 여부는 별도 확인 대상으로 둡니다.

3. 화면별로 들어갈 내용

3-1. 환자 목록·공통 탐색

목적: 다른 환자의 기록이 섞이지 않도록 진료 대상을 먼저 선택합니다. 목록에는 이름, 나이·성별, 주소증 요약을 두고, 상단에는 선택한 환자 이름과 식별 정보를 계속 표시합니다. 신규 환자 등록 시 연락처·이메일은 안내 용도와 동의 상태를 구분해 받는 구성이 적절합니다.

기존 기반: 환자 id·이름·나이·성별·이메일·전화·주소증·생성일 데이터와 환자 선택 흐름이 있습니다. 추가 후보: 녹음·안내 수신 동의, 의료기관별 권한, 환자 전환 중 진행 작업 경고입니다. 등록·수정 세부 동작과 권한 처리는 실행 검증이 필요합니다.

3-2. 환자 홈·진료 이력

들어갈 내용: 마지막 방문과 누적 방문 횟수, 주소증, 이전 처방, 통증 경과, 날짜별 방문 목록, SOAP 작성 여부, 메일 이력입니다. 주요 행동은 오늘 진료 시작, 과거 방문 열기, 호전도 리포트 보기입니다. 방문 목록과 기록 미리보기는 기존 화면 코드에 있습니다.

신규 확장 후보: 환자의 최근 걱정과 이해도, 지난 안내 후 반응, 아직 확인하지 않은 질문을 요약합니다. 임상 경과와 감정·반응을 별도 영역으로 표시하고, 과거 기록과 오늘 관찰의 날짜를 명시합니다. 자동 판단 결과는 근거 없이 환자의 확정적 상태로 표시하지 않습니다.

3-3. 오늘 진료: 녹음·전사

들어갈 내용: 환자 고정 헤더, 녹음 시작·종료와 경과 시간, 파일 업로드, 전사 중 상태, 편집 가능한 전사문, 저장 상태, 실패 사유와 재시도, 미완료 녹음 복구 목록입니다. 마이크 권한 거부·빈 파일·25MB 초과 시 다음 행동을 구체적으로 안내합니다. 녹음·전사·복구 흐름은 기존 코드에 있습니다.

신규 확장 후보: 의사·환자 발화 구분, 처방명·약재명·혈자리 후보와 불확실 표시, 원문과 수정문 비교, 진료별 녹음 연결입니다. 원음을 바꾸지 않고 수정 이력을 남기며, 긴 오디오는 분할 기준과 재조합 순서를 보장해야 합니다.

3-4. 오늘 진료: SOAP 검토

들어갈 내용: S/O/A/P 카드, 변증과 근거, 통증 점수, 차팅 옵션, 생성 버튼, 생성 실패 상태, 저장·복사입니다. 왼쪽 전사문과 오른쪽 SOAP를 나란히 보여 주면 대조하기 쉽습니다. 생성·저장·복사와 차팅 옵션은 기존 기반이고, 정밀한 근거 연결은 신규 후보입니다.

신규 확장 후보: 각 문장에 근거 발화·방문일·출처 표시, 과거 정보와 오늘 정보를 다른 표식으로 구분, 불확실한 용어와 충돌 정보 확인 목록, 의료진 검토 완료 상태입니다. 자동 진단이나 처방 확정 화면이 아니라 의료진이 검토하는 초안으로 표시합니다.

3-5. 과거 방문 상세

들어갈 내용: 해당 방문 날짜, 전사 원문, SOAP, 수정·저장·취소, 수정 전후 비교, 복사, 삭제 확인, 해당 방문과 연결된 안내 이력입니다. 전사·SOAP 편집과 수정 이력 비교 화면 코드는 기존에 있습니다. 추가 후보는 수정자·수정 이유와 원문 음성 구간 연결입니다.

3-6. 호전도 리포트

들어갈 내용: 기간과 방문별 통증 변화, 주요 증상과 처방 변화, 필요한 측정치, 한의원·담당의·발행일·서명, 참고용 자료 고지입니다. 리포트와 그래프·처방 변화·서명 영역은 기존 코드에 있고, 세부 입력·출력 동작은 추가 검증이 필요합니다.

입력 후보: 통증·기능·수면·기력·기분·복약 횟수·부작용을 필요한 만큼만 받습니다. 기존 타입에 이 항목들이 있다는 사실과 실제 환자가 집에서 입력하고 의료진 화면에 동기화되는 기능은 구분합니다. 의료기기 자동 수집 또는 AI 기반 호전 예측 기능도 확인된 것은 아닙니다.

3-7. 복약 안내·메일 관리

들어갈 내용: 수신 환자와 이메일, 처방명·기간·하루 복용 횟수·추가 안내, 생성된 안내문 미리보기, 의료진 확인, 발송 결과와 실패 사유, 이력입니다. 안내문 생성과 미리보기·메일 발송 API는 기존 코드입니다. 미리보기와 실제 발송을 UI에서도 명확히 구분하는 것이 좋습니다.

주의: 기존 API는 미리보기 문안을 확정 저장한 뒤 그 문안만 보내는 구조로 확인되지 않았고, 발송 요청에서도 LLM으로 안내문을 생성합니다. 검토한 문안과 실제 발송 문안이 동일하게 유지되는지 확인해야 합니다. 수정 가능 여부·재발송 세부 동작도 추가 확인 대상입니다.

3-8. 후속 관리: 카카오톡 모의 발송·맞춤 티칭

[신규 기획] 화면에는 이전 상태와 이번 반응, 판단 근거 발화·날짜, 의료진이 확인한 해석, 후속 문자 초안, 설명할 주제와 순서, 연락 시점 제안, 승인·보류, 환자 반응과 다음 진료 반영 내용을 둡니다. 기존 복약 이메일과 별도 기능으로 구분합니다. 동시 기획 대화에서 승인된 첫 버전 분석 범위는 걱정·불안의 대상, 효과에 대한 기대·의문·직접 표현한 실망, 이해 부족, 실천 어려움입니다. 전사문에서 근거 발언을 추출하고, 과거·현재 모두 직접 근거가 있을 때만 변화를 표시합니다. 의료진 확인 후 안내 유형과 모의 카카오 메시지를 생성하며, 목소리 기반 감정 판단이나 이탈 예측은 하지 않습니다.

데모 예시: 치료 전 걱정을 표현한 가상 환자에게는 걱정의 구체적 지점과 설명할 내용을 제안합니다. 재진에서 효과를 의심하는 반응을 보이면 이전 경과와 현재 증상을 비교하고 확인 질문·티칭 초안을 달리합니다. 이는 신규 기획 예시이지 강연의 직접 사례나 기존 구현으로 확인된 내용이 아닙니다.

판단 원칙: 감정과 이해도는 AI 해석 후보이며 확정 진단이 아닙니다. 명시된 발화와 의료진 판단을 분리하고, 근거가 부족하면 확인 필요로 표시합니다. 환자의 부작용·악화·위험 신호는 긍정적 안내로 덮지 않고 의료진 확인 대상으로 올립니다.

발송 방향: 동시 기획 대화에서 공유된 최신 방향에 맞춰 카카오톡 모의 발송으로 구성합니다. 초안·미리보기·의료진 검토·모의 발송 결과·안내 이력을 보여 주고, 실제 환자에게 전송하지 않습니다. 실제 카카오톡/SMS 연동은 신규 구현으로 확인되지 않았으며 이번 mock과 구분합니다. 향후 실발송에는 수신 동의·수신 거부·승인 문안 고정·중복 방지가 필요합니다.

3-9. 공통 검색·설정

검색에는 환자·기간·증상·변증별로 기록을 찾고 해당 방문으로 이동하는 구성을 제안합니다. 검색 페이지 경로와 저장 검색 타입은 기존에 있지만, 모든 검색 옵션의 실행 결과는 확인하지 않았습니다. 현재 구현과 새 출처 검색 기능을 구분해야 합니다.

설정에는 한의원 이름·주소·로고·담당의·서명, 차팅 기본 옵션, 연락 동의와 개인정보 보관 정책을 구분합니다. 한의원 정보와 차팅 옵션 저장 구조는 기존에 있고, 보관 정책·기관 권한·연락 동의 관리는 신규 검토 영역입니다. 요금 안내 페이지는 경로만 확인했으며 실결제 구현으로 간주하지 않습니다.

4. 기존 구현과 신규 개발의 경계

기존 기능을 유지하거나 다시 구현하는 영역: 환자·방문 구조, 녹음·업로드·일반 한국어 전사, 녹음 임시 저장과 복구, 한의학 SOAP, 재진 요약, 기록 편집·복사, 복약 안내 이메일, 이력과 리포트 화면입니다.

이번에 개선할 영역: 한의학 용어 전사 정확도, 의사·환자 발화 구분, 과거와 현재 사실 구분, 근거 구간·날짜·출처 연결, 복구 안정성, 긴 파일 처리, 검토 문안과 발송 문안 일치, 데이터 보존입니다. 재진 요약과 녹음 복구 전체를 완전히 신규라고 표시하지 않습니다.

이번 신규 확장 후보: 감정·반응 변화 요약, 근거를 보여 주는 의료진 검토, 맞춤 문자·티칭 초안, 후속관리 이력과 환자 반응, 다음 진료 연결입니다. 기분 점수 필드가 기존에 있어도 이 전체 관리 흐름이 구현돼 있다는 뜻은 아닙니다.

강연과 제품 제안의 경계: 부모 기획 페이지는 고객 여정의 변화 지점에 맞춘 연락과 케어 중심 소통을 참고 방향으로 정리하고 있습니다. 구체적인 감정 분류, 자동 감지 방법·성능, 불안·효과 의문별 생성 시나리오는 이번 제품에서 정한 설계 또는 데모 예시이며 강연에서 이미 검증된 기술이라고 설명하지 않습니다.

5. 기술 구조와 저장할 데이터

확인한 기존 구조: React + Wouter 프론트엔드, Express API, OpenAI 전사·텍스트 생성, 브라우저 localStorage 기반 환자·진료 기록입니다. 부모의 Next.js는 이번 제출 기획안의 기술 후보이며 기존 Replit 코드 구조와 동일하지 않습니다. 이번 기술 선택은 별도로 확정합니다.

기존 데이터: Patient에는 id·기본 정보·연락처·주소증·생성일이 있습니다. Consultation에는 id·patientId·날짜·전사·SOAP·선택적 처방·통증 점수·수정 이력·삭제 표시가 있습니다. MailLog에는 환자·방문 연결, 안내문, 성공 여부·메시지 식별자·오류 등의 필드가 있습니다.

새 데이터 제안: 원음/전사 구간, 발화자, 원문·수정문, 전문 용어 후보, 방문·날짜·출처를 연결합니다. 감정·반응은 근거와 해석 후보·확인자·확인 시점을 따로 남깁니다. 후속 안내에는 유형·초안·승인 문안·수신 동의·상태·환자 반응·다음 확인 사항을 저장합니다.

저장 주의: localStorage는 브라우저를 지우거나 다른 기기로 이동하면 기록이 유지·공유되지 않을 수 있습니다. 의료정보의 서버 저장, 백업, 암호화, 기관별 접근 권한, 감사 이력, 보관·삭제 정책이 검증된 시스템으로 설명하지 않습니다. 데모는 가상 환자·가상 진료 데이터로 구성합니다.

6. 해커톤 구현 우선순위 제안

P0: 가상 환자 한 명의 초진·재진으로 핵심 흐름을 끝까지 연결합니다. 전사 → 용어·근거 검토 → 과거/현재를 구분한 SOAP → 의료진 확인 → 복사까지 안정적으로 동작하는 데 우선 집중합니다. 기존/재구현/개선 부분을 기록합니다.

P1: 같은 환자의 반응이 달라지는 두 상황을 넣고 서로 다른 안내·티칭 초안을 생성합니다. 카카오톡 미리보기 → 의료진 검토 → 모의 발송 → 이력을 연결하고, 모의 처리임을 화면에 명시합니다. 분석은 승인된 전사문 기반 반응 항목으로 제한하고, 세부 모델·프롬프트·정확도는 별도 구현·검증 대상으로 둡니다.

P2: 기간별 리포트, 검색, 인쇄, 한의원 브랜딩 등 보조 화면을 다듬습니다. 전체 의료기관 관리 시스템이나 실결제·실제 환자 외부 체크인을 한 번에 구현하려고 범위를 넓히지 않습니다. 이 우선순위는 최종 확정안이 아닙니다.

7. 데모와 검증 기준

데모 순서: 가상 환자를 선택하고 이전 방문 요약을 확인합니다. 오늘 오디오를 전사해 처방명·혈자리 등 용어를 검토합니다. SOAP를 생성해 근거와 과거/현재 구분을 확인하고 수정·복사합니다. 마지막으로 반응 변화에 따라 달라진 문자·티칭 초안과 의료진 검토 화면을 보여 줍니다.

전사·차팅 검증: 정답 전사와 비교해 전문 용어의 오류·누락, 의사/환자 혼동, 없는 사실의 생성, 과거 정보의 현재 사실 오인, 검토·수정 시간을 측정합니다. 일반 방식과 개선 방식을 같은 데이터로 비교하며, 아직 측정 결과는 없습니다.

복구·저장 검증: 네트워크 단절, 마이크 권한 거부, 페이지 새로고침, 중단 녹음, 25MB 초과, 환자 전환, 날짜 경계, 중복 요청에서 데이터 손실·다른 환자 연결·중복 생성이 없는지 확인합니다. 임시 청크 저장이 파일 용량 제한을 해결하는 것은 아닙니다.

후속 안내 검증: 같은 사실에서 환자의 반응만 바꿨을 때 안내의 주제·톤·확인 질문이 적절히 달라지는지, 근거 없는 감정 단정이나 효과 보장 문구가 생기지 않는지, 검토 문안과 발송 문안이 동일한지 확인합니다. 실제 발송·연락 자동화의 성공은 별도 검증입니다.

발표에서 구분할 내용: 기존 Replit에서 확인한 기능, 당일 새로 구현하거나 개선한 기능, 모의 처리한 기능, 아직 검증되지 않은 기능을 분리해서 공개합니다. 실제 의료정보·녹음·연락은 동의와 권한이 필요한 별도 운영 범위입니다.
